FINDING 8: module-singleton renderers mutated via setWidth per call
====================================================================
Priority: high (correctness hazard, currently latent)
Risk: medium — API refactor touching all call sites; behavior must not change.

Problem
-------
`terminalRenderer` and `diffRenderer` are module singletons
(src/rendering/terminal-markdown-renderer/markdown-renderer.ts lines 39/41).
`parseMarkdown(input, width)` and `diffLines(part, width)` mutate the
singleton's shellWidth immediately before parsing:

    terminalRenderer.setWidth(width);
    return marked.parse(input, ...);   // reads this.width synchronously

This is only safe because every consumer parses synchronously inline
(marked async:false, React render is synchronous per component). It is a
fragile contract:
- Any deferred/async parse renders at ANOTHER component's width, silently.
- parseMarkdown's signature promises purity (input, width) -> string that
  the implementation does not have: the width is a hidden parameter.
- Three different notions of "current width" coexist: raw `columns`
  (user-input-request-dialog.tsx), `columns - 4` (chat-message-content.tsx
  PARSE_WIDTH_RESERVE), and process.stdout.columns at module load
  (TerminalRenderer/DiffRenderer constructor fallback, stale after any
  resize until the first setWidth; only affects `hr` rendering).

What to do
----------
Make width an explicit per-parse parameter instead of instance state:
- TerminalRenderer: replace shellWidth/setWidth with a width argument on the
  methods that consume it (hr(), reflowText) or pass width through
  marked's options per parse call — read marked's API in node_modules and
  pick the mechanism that does NOT require a mutable instance field.
- DiffRenderer.renderDiff(part, width): drop setWidth and the constructor
  width seeding (DEFAULT_SHELL_WIDTH fallback stays for non-TTY).
- markdown-renderer.ts: parseMarkdown/diffLines stop mutating singletons.
- Reconcile the width conventions while touching call sites: decide ONE
  semantic ("width the rendered blocks may occupy") and make
  user-input-request-dialog.tsx apply the same reserve logic as
  chat-message-content.tsx, or document explicitly why they differ.

Constraints
-----------
- Singletons themselves may stay (stateless after this change); do not
  introduce per-component renderer instances as a drive-by.
- The constructor's process.stdout fallback comment (NaN guard for non-TTY)
  must survive in some form.
- No behavior change: all existing tests must pass unchanged except where
  they assert on setWidth itself.
